# 本地断电与恢复备案

日期：2026-11-10。用户允许本地CPU慢跑，提醒机器可能断电。本文件记录真实实验启动前的实现与验收要求；**当前尚无真实模型运行器，以下续跑功能尚未实现或验证**。不修改系统电源设置，不承诺断电后自动开机或自动运行。

## 固定的研究决定

- 主任务：转写、意图分类；情绪配对仅为历史示例。
- 公开数据：LibriSpeech dev-clean、MINDS单一英语子集；各10–20条工程试点，子集ID在推理前固定，不按失败挑选。
- 允许本地CPU；不购买API或云GPU。先一条测时，再短批次执行，不一次投入6400次推理。
- 不再以安全对齐作为当前必做目标，调整标题无需导师批准。

## 开始长任务前必须保存什么

每次实验有独立 `runs/<run-id>/`。启动前保存不可变的 `run-spec.json`：代码提交、环境版本、模型checkpoint与revision、数据revision与许可来源、样本ID/哈希、任务、提示词、解码设置、扰动及种子、评分政策、启动命令。缺少模型或数据版本时不得把运行标记为正式可复现结果。

先检查可用磁盘；数据与权重优先使用现成下载器的缓存/续传功能。下载未完成的文件不能进入样本清单，完成后核对哈希。缓存与结果分开，恢复时不重新下载已验证文件。

## 每完成一条立即保存

使用Python标准库SQLite作为运行台账，避免自写日志恢复框架：事务内保存请求键、原始回答、开始/结束时间、状态和错误信息，配置 `synchronous=FULL`。请求键必须包含完整运行配置指纹、源音频哈希、任务、模型版本、扰动条件及重复次数；仅样本编号相同不足以复用结果。

状态区分 pending / running / completed / failed。保存答案与标记completed必须在同一事务完成，不能先标完成再写答案。模型成功返回空文本仍是completed，并按评分政策处理；加载失败、超时和断电不是模型错误回答。每次尝试保留独立编号，不用重试覆盖此前记录。

尽量把小型原始回答存入数据库事务，避免数据库和外部结果文件状态不一致。生成的音频先写临时文件，关闭并核验后再改为正式名称；汇总JSON/CSV是可重新生成的派生文件，不能作为唯一进度依据。

SQLite事务提高进程中断后的恢复能力，但无法保证抵御磁盘损坏或所有硬件断电故障。每个短批次完成后用SQLite备份接口制作带时间戳的备份并检查完整性；不要直接复制正在写入的数据库充当可靠备份。同盘备份不抵御整盘损坏；跨设备备份位置尚未指定，不擅自上传音频或结果。

## 断电后怎样恢复

1. 用户开机后，由当前工作任务检查台账和备份完整性；不假设系统自动启动任务。
2. 比较run-spec和当前配置指纹。配置发生变化则新建run-id，不混合新旧结果。
3. 仅复用有完整结果且配置一致的completed请求；中断留下的running转为interrupted尝试，重新排队。保留失败原因和重试次数。
4. 按原清单和种子继续，不重新抽样。当前正在推理而未提交的一条可能重算；已提交的结果不重复计入评分。确需重试时使用相同请求配置。
5. 从台账重建汇总，分别报告计划、尝试、完成、失败、待完成数量，以及两侧共同完成的配对数。未跑完的数据只能标记为部分结果。

CPU一次只跑少量样本，先测量单条耗时与内存。进程中断后不保证从模型内部某个token继续；目标是以完整请求为单位恢复。模型非确定性可能使被重算条目改变，因此保留尝试记录与随机设置。

## 真实长跑前的验收门槛

用小型假模型测试：完成几条后强制终止子进程，再恢复；核对已完成项不重复、未完成项补齐、没有半写回答进入评分、配置变化拒绝复用、重算汇总与完整运行一致。另测数据库损坏检测和备份恢复路径。此类进程中断测试不等于物理断电保证；不要求用户实际拔电测试。

只有以上门槛通过，才能把运行器描述为支持断点续跑。当前仅完成方案备案，未下载新模型、未启动长时间推理、未开启每日自动任务。
